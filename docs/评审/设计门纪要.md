## 2. 评审形式与手册要求的差异

| 项 | 手册要求 | 实际执行 |
|---|---------|---------|
| 组织形式 | 技术方案评审会，**架构师主持**，对齐 PRD 与 UI 稿（3.3 节关键活动 4） | 未召开会议；发起人单人简化评审 |
| 参与角色数 | ≥ 2 名不同角色（第 2 节） | 1 人 |
| 评审覆盖版本 | 提交评审的版本 | **仅 v0.1 经过评审会**。v0.2 自述"设计评审会补充确认"（实际无会议，为发起人同日决议），**至今无任何形式评审或追认**；v0.3（JDK 21 + Boot 4.1）、v0.4（**账号上下文 DDD 四层重构，ADR-012**）原从未经任何形式评审——追认材料于 2026-09-11 归档（[v0.3/v0.4 追认纪要](技术方案追认纪要.md)，[CR-018](../变更日志/变更台账.md)），**并已于同日由发起人签署「②有条件追认」（范围 A + B + C，[CR-020](../变更日志/变更台账.md)），A3-2 就此闭环**，所附三条件生效为 **A3-9 / A3-10 / A3-11** |
| 纪要归档 | 归档至 `docs/`（4.1 节） | 当时未归档，本文件为补录 |

> **本节最重要的一条**：v0.4 的 DDD 重构不仅已评审缺失，而且**已落地实现**（`module/account` 四层目录已存在，重构当时 14/14 单测通过；2026-09-11 复测为 **45/45 全绿**，见追认纪要 §2.1）。即"先改代码、后无评审"，与手册 3.3"开发可直接依据文档开工"的意图相反——文档是在实现之后追写的。
