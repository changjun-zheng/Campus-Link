## 2. 怎么登录（**本系统没有密码**）

登录 = **邮箱 + 6 位验证码**，全流程只有这一步凭据：

1. 打开 `http://localhost:5173/login`，停在「登录」Tab；
2. 填入 §3 里任一**登录邮箱**（如 `dev-stu-01@dev.campuslink.local`）；
3. 点「获取验证码」；
4. 验证码填 **`123456`** —— 这是开发期固定码（`campuslink.captcha.fixed-code`，后端启动时打 WARN），**生产必须留空**，留空后须从后端日志捞码（`CODE_SENDER_MODE=log` 下行格式 `[DEV] captcha for <邮箱> => <6位码>`）。

**关于"密码"**：本系统从设计到实现都**没有密码字段**（V1 / V2 迁移无 `password` 列，`src/main/java` 零引用）。发起人原话里的"账号和密码"，落到本系统即"邮箱 + 验证码"，故本清单**不设密码列**。若确实需要密码登录，那是 [PRD](../需求/产品需求文档.md) F-ACC-001 的**需求变更**，须另开 CR 走流程，不能由本清单代答。

**两个会撞上的限制**（都属既有设计，非缺陷）：

- **验证码重发间隔 60 秒**（`campuslink.captcha.resend-interval-seconds`）：60 秒内重复点「获取验证码」返回 `2002`，且**原验证码已被上一次校验消耗**，此时登录会得到 `2005 邮箱或验证码错误`。等过 60 秒重新获取即可；
- **学籍核验 10 次/小时/IP**（`campuslink.verify.ip-hourly-limit`）：只影响**注册**链路，不影响登录。批量灌数据时用 `VERIFY_IP_HOURLY_LIMIT=<n>` 临时抬高（见 §4）。

## 4. 怎么重建（清库后 / 换机器时）

脚本默认 **dry-run**，只读不写；加 `--apply` 才真发请求。

```bash
# 前置：本机 MySQL(campuslink 库) + Redis 已起，后端已启动，且 venv 已就绪（backend/scripts/.venv）
cd backend/scripts

# 干跑：只看会做什么 + 当前库里有多少
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe data/D001__seed_dev_roster_45.py

# 真跑：名册导入 + 45 个账号注册 + 抽 3 个账号登录复核
# ⚠️ 必须指向一个 APP_ROSTER_BYPASS=false 的实例，否则学籍核验走内置名册、这 45 个学号一律 2101
APP_ROSTER_BYPASS=false VERIFY_IP_HOURLY_LIMIT=60 SERVER_PORT=8089 mvn -o spring-boot:run   # 另起一个实例（backend/ 下）
API_BASE=http://localhost:8089 PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe data/D001__seed_dev_roster_45.py --apply
```

**为什么必须 bypass=false**：`campuslink.roster.bypass=true`（开发默认）会把 `InMemoryTestRosterGateway` 顶上来、**遮蔽数据库名册**，此时数据库里那 45 行对学籍核验完全不可见。**登录不受影响**（登录只查 `users`，不碰名册），所以日常联调用默认配置即可，只有**重建这批账号**时才需要临时关旁路。

**幂等**：名册侧服务端 `saveIfAbsent`，重跑得到 `inserted=0 skipped=45`；注册侧学号已占用 ⇒ 学籍核验返回 `2101` 被跳过，**不会产生重复账号**（2026-09-15 已实测两次连跑）。

其他可用开关：`DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD`、`ADMIN_EMAIL`、`CAPTCHA_CODE`、`LOGIN_CHECK`（登录复核个数，默认 3）、`CAPTCHA_RESEND_WAIT`（遇 `2002` 的等待秒数，默认 61）、`--stage {roster,register,all}`。

## 5. 怎么清理

```sql
-- 先删账号（外键无约束，但业务上先删用户更清晰）
DELETE FROM users WHERE nickname LIKE '模拟学生%';
DELETE FROM student_roster WHERE source_batch = 'dev-sim-45';
```

⚠️ **不可逆的一点**：若这批账号已经发过帖 / 回过帖，删 `users` 会让 `posts.user_id` 悬空（无外键约束，不会报错，但列表页昵称会变空）。**清理前先确认这批账号有没有产生内容**；有内容就不要删账号，只删名册行。

## 6. 边界与红线

- 本清单与这批数据**只对本机开发库有意义**：`campuslink.roster.bypass` 生产必须为 `false`、`campuslink.captcha.fixed-code` 生产必须**留空**——两者都是 [AGENTS.md](../../AGENTS.md)「红线」小节点名的**上线检查清单项**，发布阶段的落地载体是[发布检查清单模板](../模板/发布检查清单模板.md)；
- 名册导入**写了审计日志**（`audit_logs` 表 `action=ROSTER_IMPORT`，含批次与 inserted/skipped/failed 计数），满足"名册导入必须写审计日志"的生产红线；
- 学号在库里仍是 `student_id_enc`（AES-GCM）+ `student_id_hash`（HMAC），**本清单的明文只存在于这个文档和脚本里**，属"合成身份的开发期便利"，不改变任何接口的返回口径（任何接口仍不得返回 `*_enc` / `*_hash`）；
- **B1 / B2 真实名册到位后**：这批模拟数据应按 §5 清掉，再做一次关闭 bypass 的全链路回归（届时 `RosterGatewayDbImpl` 才是首次被真实数据验证）。
