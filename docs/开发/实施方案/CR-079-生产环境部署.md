## 1. 目标

回答"这个项目如何进行部署"：给出一套**单人可运维**的容器化部署方案，使 Campus-Link 能以 `prod` profile 在容器里稳定跑起来，并让"能不能上"这件事在动手花钱之前就被验证完。

三条硬判据（本文所有设计的收敛点）：

- **判据一**：前后端**必须同源**（Nginx 反代 `/api`），否则前端不可用——这是代码里的硬约束，不是偏好（见 §6-K5）。
- **判据二**：生产库**必须是空库由 Flyway 自建结构**（`baseline-on-migrate=false` + `validate-on-migrate=true` + `clean-disabled=true`），手工导 SQL 会绕过迁移历史。
- **判据三**：`prod` profile 下 `ProductionSafetyGuard` 八项校验不通过即**启动失败**，漏配不再"静默跑在弱安全模式"。

## 3. 部署形态推荐

### 3.1 三场景对比

| 维度 | ① 本机 Docker 全栈验证 | ② 校园内网试点 | ③ 公网云主机正式 |
|------|----------------------|---------------|-----------------|
| 面向对象 | 开发者本人 | 校内邀请制内测用户 | 全校（含宿舍 / 校外） |
| 现金成本 | **0** | **0**（用现成机器） | 域名 + 云主机，量级数百元 / 月（以官网实时报价为准） |
| 前置条件 | Docker Desktop 已起；`mvn package` 与 `npm run build` 已产出 | 一台**常开**的校内机器（建议 ≥8G 内存）+ 校内 IP 或端口放行 + 与网络管理方的口径确认 | **A3-8 签署选 A** + 域名 + ICP 备案（1~3 周）+ 云主机 + 可用 SMTP + 真实学籍名册 |
| 合规压力 | 无 | 低（校内服务；是否需向信息中心报备**由校方口径决定**，本文无法判定） | 高（ICP 备案 + 内容审核机制义务） |
| 能验证到什么 | `prod` 启动守卫、Flyway 空库建表、Nginx SPA fallback、同源 `/api` 反代、**反向验证**（故意漏配是否真的启动失败） | 真实用户注册/发帖链路、SMTP 送达、名册核验、备份恢复 | 全部（含 HTTPS、公网限流真实 IP） |
| 验证不到什么 | 真实网络延迟、真实并发、公网限流 IP、HTTPS 证书链 | 校外 / 宿舍访问、备案与 HTTPS 流程 | — |
| **推荐理由** | 花 0 元把 ③ 的全部技术风险提前暴露；是 ②③ 的唯一低成本预演 | 与 PRD §5.2"邀请制内测 → 面向全校"第一步吻合；零现金成本即可拿到真实用户反馈 | 与决策材料"建议方案 A"一致：产品定位天然覆盖宿舍/校外，内网方案在第二步失效 |
| **反对理由** | 不是"上线"，只是演练；**不能当作验收结论**（无 HTTPS、无真实网络） | 若宿舍走运营商宽带（不在校园网内），试点用户被砍掉一大半；机器断电/校园网策略变化不可控；单人项目还要自己当网管 | 成本与备案窗口是真实负担；且**机审 F-SAFE-001 未接入就公网开放，是我的明确反对项**（§10-2） |

### 3.2 推荐顺序与理由

**推荐：① → ② → ③，且 ① 无论如何都要做。**

理由：三个场景共用**同一套**容器编排与环境变量（技术方案 §8 称其为"与形态无关的固定项"：Docker Compose 编排、Flyway 迁移、dev→staging→prod 三环境）。① 做完，② 只是换台机器跑同一套 compose；② 做完，③ 只是加域名、HTTPS 与备案。**① 是唯一能以零成本证伪整套方案的一步**——若 ① 都跑不通（例如 `prod` 启动守卫误伤正常配置、SPA fallback 不生效），后面两步花的钱和时间都白搭。

与决策材料的关系：材料建议方案 A（公网）的核心动因是"**备案是排期风险而非技术风险，可与开发并行启动**"。本文完全接受这一判断并强化它——**域名注册与 ICP 备案应在做 ① 的同时就开始办**，它是唯一有外部时间窗口的事项，其余全部可以等人。

> **关于"有没有免费 / 零成本的线上方式"**：见 §9。本文给的主流免费档结论是——**演示/验收用 Cloudflare Tunnel，长期零现金托管只有 Oracle Always Free ARM 能扛住这套全栈，Render / Railway / Fly.io 物理不可用（512MB vs MySQL 700MB）**。

## 4. 容器化设计（骨架，可直接照稿实施）

### 4.1 容器清单与拓扑

```
         浏览器 ──(同源 HTTPS/HTTP)──▶ nginx(:80/:443)
                                          │
                                          ├── /              → 静态产物（frontend/dist 只读挂载）
                                          ├── /api/**        → proxy_pass http://backend:8088
                                          ├── /actuator/health → 仅此一个 actuator 端点
                                          └── /api/docs/**   → return 404（生产封文档面）
                                          │
   compose 网络 campuslink（仅内部可达，不映射宿主机端口）
     ├── mysql:3306   （卷 mysql-data，空库由 Flyway 自建结构）
     ├── redis:6379   （卷 redis-data，AOF）
     └── backend:8088 （无宿主机端口映射）
```

设计取舍：**MySQL 与 Redis 不映射任何宿主机端口**。它们只在 compose 网络内可达，攻击面从"全公网"缩到"能进容器网络的人"。开发期 `docker-compose.dev.yml` 映射 33061/63790 是因为本机要连，**生产没有这个需求**。

### 4.2 `backend/Dockerfile`（多阶段构建）

**基础镜像选型与理由**

| 阶段 | 镜像 | 理由 |
|------|------|------|
| build | `maven:3.9-eclipse-temurin-21` | 与 `pom.xml` 的 `java.version=21` 同版本；Maven 3.9 兼容 Spring Boot 4 插件；官方镜像自带 JDK 21 |
| run | `eclipse-temurin:21-jre-jammy` | ① **只要 JRE**，不带编译器，比 JDK 镜像小约 100MB；② Ubuntu jammy 是 glibc，JDBC / JJWT 等 native 相关依赖无 musl 兼容风险；③ 有 shell 与包管理，线上排查（`apt install curl`、`jcmd`）不至于抓瞎；④ 约 180MB，对本方案的磁盘预算不构成压力 |

> 备选 `21-jre-alpine`（约 80MB）：省 100MB 体积，代价是 musl + 缺调试工具。单人项目排查成本 > 100MB 磁盘，故**不推荐**；若磁盘极度紧张再考虑。

```dockerfile
# ---------- stage 1：构建（CI / 有网环境） ----------
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /build
# 先只拷 pom，把依赖层单独缓存：改代码不会重跑依赖下载
COPY pom.xml ./
RUN mvn -B -q dependency:go-offline
COPY src ./src
RUN mvn -B -DskipTests package

# ---------- stage 2：运行 ----------
FROM eclipse-temurin:21-jre-jammy
# 时区定为 UTC：与 JDBC 的 connectionTimeZone=UTC 口径一致（CR-051），
# 日志时间戳与数据库时间不对不上账
ENV TZ=UTC
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl tzdata fontconfig \
 && rm -rf /var/lib/apt/lists/*
# 非 root 运行：容器被攻破时拿不到 root
RUN useradd -r -u 10001 -m appuser
WORKDIR /app
COPY --from=build --chown=appuser:appuser \
     /build/target/campus-link-backend-0.1.0-SNAPSHOT.jar app.jar
USER appuser
EXPOSE 8088
# MaxRAMPercentage 让 JVM 按容器内存上限自适应（默认已开启 UseContainerSupport），
# 不写死 -Xmx：同一份镜像在 2C4G 与 4C8G 上都不用改参数
ENV JAVA_OPTS="-XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError"
ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS -jar /app/app.jar"]
```

> **变体 B（推荐用于 ① 本机验证 / 无外网构建环境）**：跳过 build stage，直接 `COPY target/*.jar app.jar`。本机 Maven 走 `mvn.sh` 已能出包，容器内跑 Maven 还要重新拉一遍全部依赖（首次 5~15 分钟且可能因网络失败）。**多阶段的价值在 CI 自包含，不在本机**。

> **可选优化（不推荐首轮做）**：`java -Djarmode=tools -jar app.jar extract --layers` 分层提取，让依赖层可缓存、推送只传变动层。收益在频繁发布时才显现，首轮引入只会让 Dockerfile 变复杂。

### 4.3 `docker-compose.prod.yml`（生产编排，放仓库根）

```yaml
# 用法：docker compose -f docker-compose.prod.yml --env-file deploy/.env up -d --build
# ⚠️ deploy/.env 不入库（根 .gitignore 已忽略 .env）；deploy/.env.example 入库
services:
  mysql:
    image: mysql:8.4                 # 钉死大版本，不用浮动 tag（见 §10-5）
    container_name: campuslink-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: ${DB_NAME}
      MYSQL_USER: ${DB_USER}
      MYSQL_PASSWORD: ${DB_PASSWORD}
      TZ: UTC
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_0900_ai_ci
      - --default-time-zone=+00:00
      - --innodb-buffer-pool-size=256M
    volumes:
      - mysql-data:/var/lib/mysql    # ⚠️ 绝不挂 initdb.d：结构全交给 Flyway
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p$$MYSQL_ROOT_PASSWORD"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 60s
    networks: [campuslink]

  redis:
    image: redis:7-alpine
    container_name: campuslink-redis
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "yes", "--maxmemory", "256mb", "--maxmemory-policy", "noeviction"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 10
    networks: [campuslink]

  backend:
    build:
      context: ./backend             # 上下文限 backend/，配合 backend/.dockerignore
      dockerfile: Dockerfile
    image: campus-link-backend:${IMAGE_TAG:-latest}
    container_name: campuslink-backend
    restart: unless-stopped
    env_file: [deploy/.env]
    environment:
      SPRING_PROFILES_ACTIVE: prod   # ⚠️ 最关键的一行：不加则全部生产防线不生效
      DB_HOST: mysql                 # yml 默认 localhost，容器里必须显式指向服务名
      DB_PORT: 3306
      REDIS_HOST: redis
      SERVER_PORT: 8088              # 容器内保持默认，由 Nginx 反代，不对外暴露
      TZ: UTC
    depends_on:
      mysql:
        condition: service_healthy   # 等 MySQL 真正可连，而不是等容器 start
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS http://127.0.0.1:8088/actuator/health || exit 1"]
      interval: 15s
      timeout: 5s
      retries: 10
      start_period: 90s              # 首次启动含 Flyway 建表，给足时间
    logging:
      driver: json-file
      options: {max-size: "10m", max-file: "3"}
    networks: [campuslink]

  nginx:
    image: nginx:1.27-alpine
    container_name: campuslink-nginx
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./frontend/dist:/usr/share/nginx/html:ro
      - ./deploy/nginx/campuslink.conf:/etc/nginx/conf.d/default.conf:ro
      - ./deploy/nginx/certbot-webroot:/var/www/certbot:ro
      - certbot-etc:/etc/letsencrypt:ro
    depends_on:
      backend:
        condition: service_healthy
    logging:
      driver: json-file
      options: {max-size: "10m", max-file: "3"}
    networks: [campuslink]

volumes:
  mysql-data:
  redis-data:
  certbot-etc:

networks:
  campuslink:
```

**编排要点说明**

| 要素 | 取值 | 理由 |
|------|------|------|
| 重启策略 | 全部 `unless-stopped` | 单机部署要的是"机器重启后服务自己回来"；`always` 会让人为 `docker stop` 也被拉起，运维时反直觉 |
| 依赖顺序 | `depends_on: condition: service_healthy` | 只有 mysql/redis 真正可连，backend 才启动；否则 Flyway 抢在 MySQL 初始化前跑，报 `Communications link failure` 并退出（有 `restart` 会重试，但日志一片红） |
| 健康检查 | backend 打 `/actuator/health` | `management.endpoints.web.exposure.include` 已含 `health`；这是唯一对外暴露的 actuator 端点 |
| 卷 | mysql-data / redis-data | 数据持久化；**备份必须另做**（§6-K9），卷本身不是备份 |
| 日志 | `json-file` + `max-size 10m` × 3 | 默认日志不轮转，热榜刷新失败每 10 分钟一条 ERROR 也能在几个月内吃满小盘 |
| 端口 | 只映射 80/443 | MySQL/Redis/后端不映射宿主机端口 |

### 4.4 `deploy/nginx/campuslink.conf`（反代骨架）

```nginx
upstream backend {
    server backend:8088;
    keepalive 32;
}

# ---------- HTTP：ACME 挑战走明文，其余跳 HTTPS ----------
server {
    listen 80;
    server_name _;
    location /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    http2 on;
    server_name example.cn;          # ⚠️ 换成实际域名

    ssl_certificate     /etc/letsencrypt/live/example.cn/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.cn/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    add_header Strict-Transport-Security "max-age=31536000" always;

    # ---------- 压缩 ----------
    gzip on;
    gzip_comp_level 5;
    gzip_min_length 1024;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;
    gzip_vary on;

    client_max_body_size 5m;
    server_tokens off;

    # ---------- 后端 API（同源反代：前端 BASE='/api/v1' 是硬编码相对路径） ----------
    location /api/ {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        # ⚠️ 覆盖而非 $proxy_add_x_forwarded_for：单层反代下追加会保留客户端伪造的 XFF 首段，
        #    而 IpUtil.clientIp 取 XFF 首段 → 限流可被伪造绕过
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout    60s;
    }

    # ---------- 探活：只放这一个 actuator 端点 ----------
    location = /actuator/health {
        proxy_pass http://backend/actuator/health;
        access_log off;
    }

    # ---------- 封生产文档面（springdoc） ----------
    location /api/docs    { return 404; }
    location ^~ /api/docs/ { return 404; }

    # ---------- 静态资源：Vite 产物带 content hash，可长缓存 ----------
    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    # ---------- SPA history fallback ----------
    location = /index.html { add_header Cache-Control "no-cache"; }
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

**Nginx 配置要点与踩坑**

| 要点 | 配置 | 不这么写会怎样 |
|------|------|---------------|
| SPA history fallback | `try_files $uri $uri/ /index.html` | 直接访问 `/post/123` 或刷新子路由返回 404（路由存在但 Nginx 找不到文件） |
| `/api` 反代 | `location /api/` + `proxy_pass http://backend` | 前端 `BASE='/api/v1'` 是硬编码相对路径，**不反代则全站接口 404** |
| 静态缓存 | `/assets/` 长缓存 + `index.html` `no-cache` | 反过来写会出经典故障：index.html 被缓存 → 发新版后用户仍加载旧 chunk 文件名 → 白屏 |
| gzip | 对 js/css/json/svg 开 | dist 1.3M，首屏 JS 是主要体积，移动网络下差异明显 |
| X-Forwarded-For | 用 `$remote_addr` **覆盖** | 见 §6-K6：限流 IP 失真（全站 10 次/小时）或可被伪造绕过 |
| 封 `/api/docs` | `return 404` | 对外暴露全部接口签名与错误码，等于给攻击者发地图 |
| actuator | 只放 `/actuator/health` | 其余端点即便未暴露也别转发，减少试探面 |

> **内网形态简化**：无域名时删掉 443 server 块，只留 80；`server_tokens off` 与 `/api/docs` 封禁仍建议保留。

| **K8** | **`@Scheduled` 多实例语义** | 明确"生产只跑 1 个 backend 实例"；compose 里不设 `replicas`、不手动起第二份 | 热榜刷新有 Redis 分布式锁（`campuslink:hot:refresh:lock`，TTL 300s）互斥 ⇒ **多实例不会重复执行**，锁未取到就跳过（幂等）。真正的问题不是正确性而是**内存翻倍**（K7）与"抢锁"带来的无谓开销。另注：若单次刷新耗时 > TTL，锁会提前过期，理论上允许第二个实例并发进入 | 在 2C2G 上跑两个实例 = 直接 OOM；锁 TTL 与刷新周期的关系（`ttl ≤ interval`）被破坏时，热榜刷新的互斥保证失效（只影响排序新鲜度，不影响正确性） |
| **K9** | **备份与回滚** | 备份脚本能产出非空 `.sql.gz`；**演练一次**"恢复 dump 到新库 + 起旧镜像"成功 | ① 每日 `docker exec mysql mysqldump --single-transaction --routines campuslink \| gzip` 落盘，保留 7~14 天（**卷不是备份**）；② 镜像打语义 tag（如 `2026-09-23-<sha>`），不覆盖 `latest`；③ **Flyway 社区版无 undo**：已 apply 的迁移不可修改，回滚要么新增前向迁移，要么**恢复 dump 到空库**（此时 `flyway_schema_history` 也随之回退，与"空库自建"口径一致） | 没备份 ⇒ 一次误操作/磁盘故障即全站数据归零；没演练过恢复 ⇒ 真出事时才发现 dump 是空的或不完整 |

### K7 内存预算表（明确回答"2C2G 能不能扛"）

| 组件 | 2C4G（最低可行） | 4C8G（推荐） | 说明 |
|------|-----------------|-------------|------|
| MySQL 8.4 | `innodb-buffer-pool-size=512M`，RSS 约 700MB | `=1G`，RSS 约 1.2GB | MySQL 8 自身空跑即需数百 MB；buffer pool 太小则列表查询大量磁盘 IO |
| backend JVM | `-XX:MaxRAMPercentage=70`（4G → 约 1.1GB 上限，含堆+元空间+栈+直接内存） | 约 2.8GB 上限 | 实测 jar 58MB；Spring Boot + MyBatis-Plus + Redis 常规堆占用 300~600MB，峰值留一倍余量 |
| Redis | `maxmemory 256mb`，RSS 约 60MB | 512mb | 存验证码、限流计数、热榜锁；`noeviction`（验证码被逐出等于注册失败） |
| Nginx | 约 15MB | 约 20MB | — |
| 系统 + Docker + 页缓存 | 约 500MB | 约 800MB | — |
| **合计** | **约 2.3GB / 4GB（58%）** | **约 4.8GB / 8GB（60%）** | 2C2G 下同样配置合计约 2.1~2.4GB > 2GB ⇒ **不推荐** |

> **CPU**：日活千级、单机部署下 2C 足够；热榜刷新每 10 分钟一次、批量 500 条，CPU 压力可忽略。真正的瓶颈是内存与磁盘 IO。
> **磁盘**：镜像（jre 180MB + jar 58MB + mysql 600MB + nginx 50MB）+ 数据 + 日志 + 备份，建议 **≥40GB SSD**；备份不要与数据卷同盘。

## 9. 低成本 / 免费线上部署路径可行性评估（2026-09-24 补充）

> 本节回应发起人追问："**有没有免费 / 零成本的线上部署方式？或者用内网穿透？**"
>
> **时效性声明**：免费档政策变动频繁，本节的时间锚点是 **2026-09**。配额口径**以 Oracle 官方文档为准**——Always Free ARM 配额**已于 2026-06 减半（4 OCPU/24GB → 2 OCPU/12GB），且自 2026-08-18 起强制回收超限实例**；网络上仍有大量未更新的旧页面在写 4 核 24GB。⚠️ **该配额不是合同，可能再次变更**，请把免费档当成"随时可能要搬家的一台机器"，而不是"永久免费主机"。

### 9.1 判定汇总

| 路径 | 判定 | 一句话理由 | 硬代价 |
|------|------|-----------|-------|
| **Oracle Cloud Always Free（ARM Ampere A1，2 OCPU / 12GB）** | ✅ **唯一能免费长期承载本全栈** | 12GB 内存远超 §6-K7 给的最低 4GB，四容器随便放 | 信用卡 `$1` 预授权核验、ARM 架构、抢容量（Out of Capacity 可能重试数天）、**空闲回收风险**、区域多在海外 |
| **Cloudflare Tunnel（内网穿透）** | ⚠️ **演示 / 验收 / 临时联调可用，不适合服务全校** | 小时级就能让校外访问本机服务，零现金成本 | ① 备案义务不因穿透而免除（合规红线）；② CF 中国大陆无节点 ⇒ 跨境延迟高；③ 跑在自己电脑上 ⇒ 家用上行带宽 + 必须长期开机成为可用性瓶颈 |
| **Render / Railway / Fly.io / Heroku** | ❌ **不可行**（资源量级差一个数量级） | Render 免费层与 **付费 Starter 档整机都只有 512MB**，而 §6-K7 的 MySQL 8 稳态就 **~700MB**——**一个 MySQL 容器自己都装不下** | Railway / Fly.io / Heroku 连"试"的机会都没有：免费层已取消，进场即按量计费 |
| **纯前端免费托管（Vercel / Cloudflare Pages / Netlify）+ 独立后端** | ⚠️ **技术上可行，但须先改代码**（独立 CR） | 静态产物 1.3M 毫无压力，但与 §6-K5 的同源硬约束直接冲突 | 必须先引入 `VITE_API_BASE`；换来跨域 + 两个部署面 + 两套证书与缓存策略 |

### 9.2 Render / Railway / Fly.io / Heroku：不可行，不要在这上面耗时间

| 平台 | 免费层现状（2026-09） | 判定 |
|------|---------------------|------|
| Render | 免费计算层 **512MB RAM / 0.1 CPU**、750 实例小时/月、**15 分钟无流量休眠、唤醒约 1 分钟**；免费 Postgres **创建 30 天后自动删除**；付费 Starter **$7/月** 也只有 **512MB RAM / 0.5 CPU** | ❌ **物理跑不起来** |
| Railway | 免费层已取消，改为 **$5 一次性试用额度**（用完即按量计费） | ❌ 不存在免费档 |
| Fly.io | 2024-10 起**新用户无免费层**（仅遗留 Hobby 账号保留） | ❌ 不存在免费档 |
| Heroku | 2022-11 起无免费 Dyno | ❌ 不存在免费档 |

**为什么写成"不可行"而不是"需要调优"**——把 §6-K7 的预算数字直接摆出来：

```
Render 整机上限        512 MB
§6-K7 MySQL 8 稳态   ~ 700 MB   ← 仅数据库一项就已超整机上限
§6-K7 最低可行全栈   ~2300 MB   （MySQL 700 + JVM ~1000 + Redis 60 + Nginx 15 + 系统 500）
```

即便把 `innodb_buffer_pool_size` 压到 64MB、JVM `-Xmx128m`，得到的也只是"MySQL 疯狂刷盘、JVM 频繁 Full GC、Redis 无处安放"的残次系统；更要命的是免费层 **15 分钟无流量休眠、唤醒约 1 分钟**——对一个"注册要收验证码邮件"的链路，等于每次冷启动都在赌超时。**这不是配置技巧问题，是资源量级差一个数量级。**

### 9.3 Oracle Cloud Always Free ARM：唯一能免费长期承载全栈的档位

**配额事实（2026-09，以 Oracle 官方文档为准）**

| 项 | 值 | 对本项目的含义 |
|----|----|---------------|
| ARM Ampere A1 Compute | **2 OCPU / 12GB**（2026-06-15 起由 4/24 减半；2026-08-18 起强制回收超限实例） | **超过 §6-K7 的 4C8G 推荐**：MySQL 可开 1G buffer pool，JVM `MaxRAMPercentage=70`，四容器无压力 |
| 配额性质 | **tenancy 级总量池**：可拆 1 台 2/12 或 2 台 1/6，合计不可超 | 本方案只用 **1 台 2 OCPU / 12GB**，全量给这一台 |
| x86 micro | 2 台 ×（1/8 OCPU + 1GB） | 太小，跑不动 MySQL。**不建议**用于本全栈（可留作备份机 / rsync 目标） |
| 块存储 | 200GB | 充足（§6-K7 建议 ≥40GB） |
| 出网流量 | 10TB / 月 | 远超"日活千级论坛"的量级 |
| 身份核验 | **需信用卡，$1 预授权后退还** | 学生的第一道门槛 |
| 架构 | **ARM（aarch64）** | 见下方构建说明 |
| 可用性风险 | 热门区域频繁 **Out of Capacity**，可能重试数天 | 抢容量是常态，不是异常 |
| 回收规则 | **连续 7 天 CPU / 网络 / 内存三项均 < 20%** 的空闲实例可能被回收 | ⚠️ 见下方"回收画像" |

**ARM 构建怎么做（免费档唯一的真技术活）**

| 组件 | linux/arm64 支持 | 说明 |
|------|-----------------|------|
| Spring Boot 4 + Java 21（本项目后端全部依赖：mybatis-plus、jjwt、flexmark、jsoup、jsqlparser、MySQL Connector/J） | ✅ | **全栈纯 Java，无 JNI / 无 native 库** ⇒ 换架构不需要改一行代码 |
| `eclipse-temurin:21-jre-jammy` | ✅ 提供 linux/arm64 manifest | 在 x86 机器上 `docker pull` 需显式 `--platform linux/arm64` |
| `mysql:8.4` | ✅ 提供 linux/arm64 manifest | — |
| `redis:7-alpine` | ✅ | — |
| `nginx:1.27-alpine` | ✅ | — |

两种做法，**推荐做法 B**：

- **做法 A（本机交叉编译）**：`docker buildx build --platform linux/arm64 -t <镜像> --push`（走 QEMU 模拟，构建很慢，Maven 阶段容易超时）。
- **做法 B（推荐：在 ARM 实例上直接构建）**：实例里装 Docker（+ 如需才装 Maven），把 §4 的 `docker-compose.prod.yml` **原样跑一遍**，Dockerfile 一个字都不用改。JAR 是平台无关的纯 Java 产物——**本机 x86 打出的 jar 与 ARM 上打出的完全等价**，所以最省事的路径是：本机保留 §4.2 的"变体 B"（直接 COPY 已构建 jar），把 `jar` 与 `frontend/dist` 传到实例上，在 ARM 本机 `docker compose build` 出镜像。

**"回收画像"里藏着一个本项目特有的陷阱**：Oracle 回收的是**连续 7 天 CPU / 网络 / 内存三项均 < 20%** 的实例。而一个刚上线的校园论坛，试点期日活个位数——**它的资源画像恰好就是"长期空闲"**。也就是说，最容易触发回收的时间窗口，恰恰是"还没用户来"的那几周。

对策（不造假、不刷量）：

1. **备份必须离开这台机器**（§6-K9 的 mysqldump 落到 OCI 对象存储免费桶 / 另一台 micro 的 rsync / 本地异地）。回收通知到手通常还有小时级窗口，但这只有在备份不在同一块盘上时才有用。
2. 打开云控制台的资源告警与邮件通知——**回收邮件要有人才有用**。
3. 把"每天登一次站做一次真实操作"写进日常：这既是产品观察，也顺带避免长期零活动。
4. compose 全部 `restart: unless-stopped`，保证宿主机重启后服务自愈。

**免费档的其余诚实代价**：**Always Free 不是合同**，配额可能再次变更、条款随时调整 ⇒ 整套方案仍应回到 §4 的标准 compose + 卷 + 备份，**迁移成本才可控**；此外区域多在海外，延迟高于境内节点，**建议先 `ping` 一次目标区域的测试 IP 再敲定区域**。

### 9.4 Cloudflare Tunnel（内网穿透）：演示可用，服务全校不可

**能力事实（2026-09）**：Zero Trust Free 计划 **$0 / 50 用户**；**隧道数量与流量不限**；单请求体上限 **100MB**（Free / Pro）；支持自定义域名但**域名必须托管在 Cloudflare**；**出站连接**方式 ⇒ 无需公网 IP、无需在路由器 / 防火墙开任何入站端口、自带 HTTPS 与 DDoS 防护。

**推荐接法**：`cloudflared` 指向本机 **nginx（80）**，而不是直接指向 backend——这样静态产物与 `/api` 仍在同一个域名下，**§6-K5 的同源硬约束依然成立**，§4.4 的 Nginx 配置一行都不用改。

| 判定项 | 结论 |
|-------|------|
| 技术可行性 | ✅ 小时级即可校外访问，零现金成本 |
| 长期服务全校 | ❌ **不推荐**，理由见下方三条 |

**三条不能静默带过的代价**

| # | 代价 | 说明 |
|---|------|------|
| **①** | **ICP 备案义务不因穿透而免除**（合规红线，不是技术取舍） | 大陆境内提供互联网信息服务的备案要求，约束的是"**是否在境内提供服务**"，而不是"有没有公网 IP / 用了什么隧道"。内网穿透绕过的是**技术门槛**，不是**备案义务**。用 Tunnel 长期对外开放 ≠ 合规。**这一条请发起人自行判断并承担，我不替发起人对合规口径下结论** |
| **②** | Cloudflare 在中国大陆无节点 | 国内访问会被调度到境外 PoP（多为美国 / 新加坡），**跨境延迟与抖动显著高于境内节点**，晚高峰波动更大。看帖尚可忍，"注册收验证码 + 发帖"这类交互链路体验很差 |
| **③** | 跑在自己电脑上 = 家用宽带 + 笔记本 | 可用性由**家用宽带上行带宽**和**是否长期开机**决定：关机 / 断网 / Windows 更新重启 = 站点下线；家用宽带上行通常远小于下行，几个用户同时看图就是瓶颈。这与"服务全校"的要求正交 |

**它的正确用法（限定这些场景才划算）**：课程答辩 / 毕业设计演示、临时给校外同学或老师远程验收、做完 §7 阶段 1 的本机全栈验证后补一次"外部真实可达"确认、名册导入与首个管理员联调（K3 / K4）。

### 9.5 纯前端免费托管（Vercel / Cloudflare Pages / Netlify）：可行，但要先改代码

| 判定项 | 结论 |
|-------|------|
| 静态产物本身 | ✅ `frontend/dist` 实测 **1.3M**，任何静态托管都毫无压力 |
| 与本项目现状 | ❌ **直接冲突**：`frontend/src/api/client.ts` 第 1 行 `const BASE = '/api/v1'` 是硬编码相对路径，全仓零 `VITE_*` ⇒ 前端托管到 `xxx.pages.dev`、后端在别处 ⇒ 所有接口请求打到前端域名下的 `/api/v1`，返回 index.html 或 404（§6-K5） |
| 解锁办法 | 引入 `VITE_API_BASE` —— **属代码变更，需单独开 CR 并评审**，本轮不写（见待确认 10） |
| 就算改了，换来什么 | 跨域（要配 `CORS_ORIGINS`、要处理预检）+ **两个部署面 + 两套证书与缓存策略** + 前后端版本错配风险。**对单人项目，这是把一份运维变成两份** |

### 9.6 推荐排序（我的结论，可反驳）

按"**零现金**"诉求的强弱排序，并给出各自的失效边界：

| 排序 | 路径 | 适用于 | 失效边界 |
|------|------|-------|---------|
| **1** | **Oracle Always Free ARM（2C12G）+ §4 标准 compose** | 想要 **0 元现金 + 长期在线** 的真实部署 | 抢不到容量 / 被判空闲回收 / 配额再变 / 不愿绑信用卡 ⇒ 退回下面的内网试点 |
| **2** | **② 校园内网试点**（§3） | 有闲置常开机器、只要校内可达 | 宿舍不在校园网 ⇒ 覆盖不到一半用户 |
| **3** | **Cloudflare Tunnel** | **演示 / 答辩 / 临时远程验收**（限定用途） | 一旦想长期服务全校 ⇒ 同时撞上备案红线 + 跨境延迟 + 家用带宽三堵墙 |
| **4** | **③ 境内公网云主机 + 域名 + ICP 备案** | 决心长期正式运营、愿意付数百元/月 | 成本与备案窗口（仍是 A3-8 未签署的建议项） |
| — | Render / Railway / Fly.io / Heroku | **不要用** | 512MB 装不下 MySQL（9.2） |
| — | 纯前端托管 + 分离后端 | 先做完那个 CR 再谈 | 未改 `client.ts` 前是死路 |

> **一句话给发起人**：**演示用 Tunnel；真要零现金长期托管就用 Oracle ARM；Render / Railway / Fly.io 连试都不必试。**
>
> 三个"免费"选项的共同底线始终是同一条：**备份必须离开这台机器（§6-K9）**。免费档最贵的部分不是钱，是一次回收赔掉全部用户数据。
