# CR-093 实施方案：手机号注册 / 登录（F-011，登记与实施同批）

| 文档信息 | 内容 |
|---|---|
| 关联 | 问题清单 F-011 · PRD F-ACC-001（"邮箱**或**手机号 + 验证码"）· V1 预留列 `users.phone_enc / phone_hash`（含唯一键） |
| 评审方式 | 发起人指令"要做" + 授权自审代批 |
| 状态 | 实施中（2026-10-10） |

## 1. 目标

把 F-011 的"手机号分支"补全：**注册**（学籍核验票据 + 手机号 + 验证码）与**登录**（邮箱**或**手机号 + 验证码）双通道，dev 用既有 log 通道全链路可测。**零迁移**——`email_enc/email_hash` 在 V1 本就可空、`phone_enc/phone_hash` 连唯一键都已预留。

## 2. 范围

**做**：① `PhoneNumber` 值对象（`^1[3-9]\d{9}$`，镜像 EmailAddress）；② 聚合 `Account` +`phone`（可空）与 `registered` 四参重载（旧三参保留、夹具零改动），`rehydrate` 加参（6 个调用点随改）；③ 转换器 phone 双向接线（emailEnc 为 NULL 的账号沿用既有占位合成逻辑）；④ 仓储端口 + 适配器 `existsByPhoneHash / findByPhoneHash`、唯一键冲突翻译 `uk_users_phone_hash` → `Field.PHONE`；⑤ **新错误码 `PHONE_EXISTS(2014, 409, "该手机号已注册")`**；⑥ Command 改版——`CaptchaCommand.target` 与 `LoginCommand.account` 改"邮箱或手机号"二合一格式门（`@Pattern` 联合正则，HTML5 email 同族 ∪ 大陆手机号）、`RegisterCommand.email` → **`contact`**（同款二合一格式门）；⑦ 应用服务 `Contact.parse` 统一解析（邮箱 / 手机号分流，验证码存取键 = 规范化 contact 的 HMAC，发送 / 校验 / 消费同键）；⑧ 前端 LoginView 注册与登录表单改"邮箱 / 手机号"单输入（按内容自动分流，CSDN 同款），api/auth.ts 与 auth store 随改。

**不做**：短信服务商对接（生产 `CODE_SENDER_MODE=mail` 下手机号发码不可用，与机审服务商同属外部依赖欠账，如实登记）；设置页绑定 / 换绑手机号（F-ACC-007 范围）；手机号找回密码（本系统无密码）；版块 / 搜索页触底加载（另行批次）。

## 3. 改动点（文件级）

**后端**：`PhoneNumber`（新）；`AccountCommands`（三 Command 改版）；`Contact`（新值对象，邮箱 / 手机号二合一解析 + 规范化取值，email 格式门采用 HTML5 email 正则——与原 jakarta `@Email` 同族，存量邮箱全部兼容）；`Account`（+phone）；`AccountConverter` / `AccountRepository` / `AccountRepositoryImpl`（phone 双向 + 两查找方法 + 冲突翻译）；`AccountConflictException.Field`（+PHONE）；`ResultCode`（+2014）；`AccountApplicationService`（register / login 分流）；`AccountController`（/captcha summary、register @ErrorCodes +PHONE_EXISTS）。**前端**：`api/auth.ts`、`stores/auth.ts`、`LoginView.vue`。

## 4. 步骤

后端 11 文件 → 单测 → `mvn verify` 全绿（基线 358 → N）→ 前端 → `npm run build` → 起栈冒烟（手机号注册 → 手机号登录 → 邮箱登录回归）→ 契约快照 v1.18 重抓（`/captcha` target、`/register` contact、`/login` account 三处形状变化 + 2014 码）→ README / 技术方案 §5 / 台账 / 问题清单 F-011 回置 / 驾驶舱。

## 5. 验证

- `mvn verify` 全绿；`npm run build` 通过；
- 真机冒烟（dev-stu 账号 + 固定验证码）：手机号注册新号 → 手机号验证码登录 → 原邮箱登录回归 → 同手机号重复注册 `409 / 2014` → 垃圾 target `400 / 1001`；
- 契约 diff 逐行归因（预期仅 auth 三端点 + 2014 码 + Preview 已在 v1.17）。

## 6. 回滚

零迁移、纯前向：revert 单提交即可。唯一数据面：手机号注册产生的行 `email_enc/hash` 为 NULL——回滚后这些账号无法登录（dev 数据，可接受）。

## 实施结果

- 单测 **358 → 366**（+8 例逐类归因：`AccountApplicationServiceLoginTest` 新类 +4（手机号查找 / 邮箱回归 / 查无账号统一提示 / 格式非法兜底）；`RegisterTest` +3（手机号渠道落库与预检通道 / 2014 映射 / 邮箱预检通道不误触 phone 预检）；`ConflictTest` +1（phone_hash 冲突翻译 `Field.PHONE`））。既有 4 处 `rehydrate` 测试夹具与 4 处 `Account.registered` 三参调用点随签名兼容（三参重载保留，夹具零改动；rehydrate 6 处调用点全部改齐）。
- 真机冒烟 8 项断言全 PASS（dev 名册 + log 通道）：学籍核验 → 手机号发码 → 手机号注册（token）→ **手机号登录** → **邮箱登录回归** → 同手机号重复注册 `409 / 2014` → 垃圾 target `400 / 1001` → 错码登录 `2005`。冒烟数据（CR093-smoke 账号 + cr093-smoke 名册两行）留 dev 库无副作用。
- 契约快照 v1.17 → **v1.18**（124053 字节）：auth 三端点 shape 变化（`contact` / `account` / target 格式门）+ register 409 补 `2014` + 三个 summary 更新；`mvn verify` 后 `el-main` sticky 修复一并验证。真机走查另确认：**登录页"邮箱 / 手机号"单输入在 5174 可用**。
- ⚠️ 两处实施偏差如实登记：① `Contact` 邮箱格式门最终采用 **HTML5 email 正则**（与原 jakarta `@Email` 同族宽进，存量邮箱全部兼容——若采用更严正则会把 `user@localhost` 一类老邮箱挡在登录之外）；② 首次冒烟 2101 的真因是**四个测试名册学号均已被历史邮箱注册占用**（张三/李四/王五/赵六=users 2/6/7/8），非手机号链路缺陷——改用 DB 名册（`CAMPUSLINK_ROSTER_BYPASS=false` + 预插 cr093-smoke 两行名册）后全链路通。
- ⚠️ 生产残余不变：`CODE_SENDER_MODE=mail` 下手机号发码不可用（短信服务商属 A3-8 族外部欠账）——**不因"手机号功能已完成"而宣称 F-011 全量达标**，dev 全链路已通。
