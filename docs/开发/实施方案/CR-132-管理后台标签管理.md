## 1. 目标

补齐 PRD P1「版块 / 标签管理」（F-ADMIN-004）中**可执行的那一半**：版块按 F-FORUM-001 固定 6 个、不支持增删，故本轮只做**标签管理**——给 SUPERADMIN 一个标签列表（搜索 / 排序）与**删除**入口，用于清理错别字 / 违规 / 无意义标签。

## 2. 范围

- **做**：
  - 两个受保护端点（仅 SUPERADMIN）：
    - `GET /api/v1/admin/tags?keyword=&sort=use_count|name&page=&size=`：分页标签列表，条目 `id / name / useCount / createdAt`；`keyword` 对名称做 LIKE；排序 `use_count`（默认，降序）或 `name`（升序）；`size` 上限 100；
    - `DELETE /api/v1/admin/tags/{id}`：删除标签（**先删 `post_tags` 关联**——`fk_pt_tag` 外键要求，再把该标签从受影响帖子的 `posts.tags` 冗余列移除（保留其余标签，空则置 NULL），最后删 `tags` 行）；标签不存在 → `404 / 3001`；每次成功删除记一条 `TAG_DELETE` 审计（detail 含标签名与受影响帖子数）。
  - 删除在**适配器内一个事务**完成（与 `attachToPost` / `replaceForPost` 同一边界表达，避免"关联已删、冗余列未清"的半截态）。
  - 前端：`AdminView` 第四 Tab「标签管理」——关键字搜索 + 排序切换 + 列表（名称 / **累计使用次数** / 创建时间）+ 删除二次确认（`ElMessageBox.confirm`）+ 分页 + 空态。
  - 契约快照重抓（预期 +2 操作 / +2 路径 / +2~3 schema / 新 tag `admin-tags`），契约 README / 技术方案 §5 / 界面规范 / 台账 / 驾驶舱回置。
- **不做**：
  - 标签**合并 / 重命名**（同义标签合流另开 CR；本轮只做删除）；
  - 新增标签（发帖时 find-or-create 已覆盖）；
  - 版块管理（F-FORUM-001 固定 6 版块、不支持用户自建）；
  - 批量删除 / 删除前预览受影响帖子列表；
  - 删除帖子的标签回退（`use_count` 是**累计挂载次数**，软删帖子不回退，展示口径在 UI 注明）。

## 8. 实施结果（实施后追加，不回改上文）

- **与计划一致**：`GET /api/v1/admin/tags`（分页 / keyword / sort）、`DELETE /api/v1/admin/tags/{id}`（事务内删关联 → 清 `posts.tags` 冗余列 → 删行 + `TAG_DELETE` 审计）、`TagRepository` 4 方法、`AdminTagApplicationService` / `AdminTagController` / `AdminTagsVo`、前端 `api/admin.ts` + `AdminView` 第四 Tab，均按 §3 落地；§7 四条口径按默认值执行。
- **偏差 1（operationId 撞车，与 CR-130 同类第二次）**：控制器方法原名 `delete`，重抓后新端点 operationId 被加后缀 `delete_1`（与既有 `DELETE /posts/{id}` 的 `delete` 重名）。改名 `deleteTag` 后重抓，既有端点保持 `delete`、新端点为 `deleteTag`，快照恢复**纯新增**（+257 / −0）。契约 README §3.10 已写明该约束。
- **偏差 2（前端确认写法）**：`onDeleteTag` 的确认从 `await ElMessageBox.confirm(...).catch(() => false)` 改为 `try { await ... } catch { return }`——语义等价、更易读；改动后浏览器复验受环境阻塞（见偏差 3），未取得二次 UI 证据。
- **偏差 3（浏览器验收边界，如实登记）**：第一轮实测已通过登录 → 四个 Tab → 标签管理 UI（搜索 / 排序 / 列表 / 说明文案）→ 搜索 `browserdel` 命中 1 条 → 删除确认框出现且文案正确；**删除真实生效**由后端证据证明——`audit_logs` 有 `TAG_DELETE target_id=9 tagName=browserdel, affectedPosts=1`、`tags` 行已删、`post_tags` 无残留、`posts.tags` 被清为 NULL。但「删除后的成功提示与列表空态」**未取得稳定的自动化观察**；此后浏览器会话连续 4 次 60s 超时（iCube 环境侧，`browser_navigate` 无法加载），无法二次复验。**不冒充该两项已观测**——UI 反馈代码路径为 `ElMessage.success` + `loadTags` 后空态，与首轮实际删除结果一并作为依据；该两项留给发起人人工走查（与 A3-6 人工走查同批）。
- **偏差 4（静态扫描）**：SpotBugs 首跑 6 条（DI 构造器 2 条 + 分页载体 4 条），按既有第 ① / ③ 组惯例加入 `spotbugs-exclude.xml`，复跑 0。
- **验证实测**：`SPRING_IT=true mvn -o verify` **574 → 587**（0 failures / Skipped 0，+13 例 / 3 个测试类）；`npm run lint` exit 0、`npm run build` 通过；契约 **v1.32**（48 路径 / 55 操作 / 85 schema / 16 tag / 42 受保护、162406 字节、+257 / −0 纯新增）。
- **真机取证（真实后端 + 真实库）**：dev-stu-09 发帖带唯一标签 `zq7x9k2v`（标题不含该词）→ 搜索命中 **1** 条（list 含该帖）→ 管理端列表 `total=1 / useCount=1` → 删除 `200` → 搜索 **0** 条、帖子详情 `tags=java`（**其余标签保留**）、`posts.tags` 只剩 `java`、`post_tags` 无残留、`tags` 行已删、审计 `TAG_DELETE`（`tagName=zq7x9k2v, affectedPosts=1`）；验证帖与临时标签全部清理。边界：匿名 `401 / 4001`、普通用户 `403 / 4002`、不存在标签 `404 / 3001`、`page=0&size=999 → 1 / 100`、`sort=name` 升序生效。
- **一条观察（非本 CR 缺陷）**：站内搜索的 `MATCH(title)` 在 ngram 下会把英文词切成 bigram，历史验证帖标题大量含 `CR-1xx`，令「任意英文关键词」容易命中大量历史帖；因此标签删除的搜索验证必须用**与历史标题无共同 bigram 的唯一词**（本轮先用 `cr132-临时` 命中了 15 条历史帖，改用 `zq7x9k2v` 后才得到 1 → 0 的干净证据）。搜索关键词的最小长度 2 与 bigram 噪声属既有行为，不在本 CR 改动范围。
- **遗留**：合并 / 重命名 / 批量删除 / 版块管理不做（方案 §2）；「成功提示 + 空态」两项浏览器 UI 反馈待人工走查。
