| 最后更新 | 2026-11-03 |

本目录存放**较大功能改造 / Bug 修复**的「可实施方案」——实施前评审的载体，规则见 [`AGENTS.md`](../../../AGENTS.md)「实施方案约定」。

## 用法

1. 判断是否够大：对照 AGENTS.md 的门槛（跨模块 / 接口契约 / 数据库结构 / 新依赖 / 安全鉴权 / 根因跨层或改变对外行为的 Bug 修复）。够大才写；普通小修直接改，不写方案、不单独登记 CR；改变基线或流程规则的任务才登记 CR。
2. 复制本文件为 **`CR-xxx-主题.md`**（编号以 change-log 最新登记为准，例：`CR-040-消息通知重试.md`——仅示形），填六节。
3. **写完停下**：报告"方案已写 + 路径 + 要点"，**得到用户同意后才动代码**；口径变了先改方案。
4. 实施完成后，把实际与计划的偏差**追加到文末「实施结果」节**，不回改上文（保留原计划 vs 实际的对照）。

**篇幅**：原方案一页以内，实施结果建议 ≤10 行；只记录结果、必要偏差、未测项与遗留项，长日志 / 截图链接引用，不记录探索过程与逐轮对话。方案不是设计文档，只写"怎么改、怎么验、怎么退"，**不复述技术方案已有内容**，需要时直接给链接。

## 1. 目标

<这次要达成什么，一两句；有量化口径就写（如"接口 P95 从 X 降到 Y"）>

## 2. 范围

- **做**：<要点列表>
- **不做**：<明确排除项——这一节比"做"更重要，防止边界漂移>

## 3. 改动点（文件级）

| 文件 | 动作 | 说明 |
|------|------|------|
| `backend/src/.../Foo.java` | 改 | <改什么> |

| `docs/设计/接口契约/openapi.json` | 重生成 | 契约快照（若涉及） |

## 4. 步骤

- [ ] 1. <可执行、可验证的单步>
- [ ] 2. <…>
- [ ] 3. 契约快照重生成 / 文档同步（若涉及）

## 5. 验证

- **单测**：<覆盖哪些行为及失败路径；不预设测试数量>
- **真机**：<起栈实测哪些路径、期望状态码与响应形状>
- **契约**：<`git diff` 快照是否应为空；非空则说明了什么>
- **回归面**：<可能被影响的既有行为，逐条确认>

## 6. 回滚

<怎么退：revert 哪个 commit / 关哪个开关 / 数据是否需要回补；不可逆部分单独点明>

## 7. 实施结果（实施后追加，不回改上文）

<实际改了什么、与计划的偏差、验证的真实结果、遗留项与后续 CR>

## 维护提示

- 方案与 CR 一一对应，**CR 编号以 change-log 为准**；不要自造编号。
- 方案里**不写版本号引用**（交叉引用只给链接，版本号只在 [`docs/README.md`](../../README.md) §2 维护）。
- 若某次改动写方案后发现根本用不上（如随手修掉了），**在方案文末注明"未实施，原因 xx"**，不要删文件——否则台账里的 CR 会失去指向。
