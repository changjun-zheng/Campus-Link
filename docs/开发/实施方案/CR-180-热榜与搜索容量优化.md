## 1. 目标

把 10 万帖规模下的 **热榜 P95 1778ms、搜索 P95 12,722ms** 压到 PRD 读接口口径 **≤ 500ms**，同时保持搜索「标题 / 正文 / 标签」三路命中与既有可见性过滤不变。

## 2. 范围

- **做**：
  1. **V10 迁移**：`posts` 增加复合索引 `idx_posts_hot_list (status, is_deleted, hot_score DESC, created_at DESC, id DESC)`——热榜查询是 `status/is_deleted` 等值 + `hot_score DESC, created_at DESC, id DESC` 排序，现有 `idx_posts_latest` 只能过滤后 filesort 49,157 行。
  2. **搜索 SQL 改写**：`PostMapper.search` 的 `OR tags LIKE` 改为 **UNION 两支**——① FULLTEXT 支（`MATCH(title)*2 + MATCH(content_md)`，保留相关度）；② 标签支（`post_tags JOIN tags`，`t.name LIKE`，相关度记 0）。两支都带原有 `status/is_deleted/board/days/拉黑/举报排除` 条件，外层按 `relevance DESC, created_at DESC, id DESC` 排序分页；分页与 total 保持现有 `page/size` 语义。
  3. 补测试：标题 / 正文 / 标签三路命中、可见性过滤继承、热榜顺序与翻页稳定。
- **不做**：不改接口路径 / 入参 / 出参 / 错误码；不引入搜索引擎或新依赖；不改前端；不动 `idx_posts_hot` 旧索引（先保留，后续按慢查询再评估删除）；不做注册 1 万 / DAU 1000 的账号与流量模拟。

## 7. 实施结果（2026-11-01）

**结论**：V10 热榜索引已实施并达标；**搜索 SQL 改写实测退化，已回退**，搜索容量另立 CR-181。

**偏差原因**：`OR tags LIKE` 确实让 FULLTEXT 失效，但 UNION 把 `p.*`（含 `content_md` / `content_html`）拖进 10 万行去重与排序，成本反而放大；且 `MATCH(content_md) … LIMIT 1` 在泛化关键词下也要 **2.4s**——瓶颈是 ngram 自然语言模式必须对全部命中打分（O(命中数)），不是 SQL 结构的单点问题。合并 FULLTEXT `(title, content_md)` 的对照方案 count 2.17s / page 8.49s，仍远超 500ms，故未采纳（临时索引已删除，未进仓库）。

**后续（CR-181，待发起人确认口径）**：① **有界检索窗口**——最近 N 条命中内排序、`total` 设上限，能进 500ms 但改变搜索语义；② **专用搜索引擎**——满足全量相关度但属新依赖 / 架构变更。二者都需先确认，不在本 CR 擅自实施。

**环境清理**：8098 验证实例已停止（PID 18944）；临时合并全文索引已删除；容量数据已清理（115 帖 / 85 楼）。⚠️ 批量删除 10 万帖后 InnoDB FULLTEXT 统计失真，`MATCH(title)*2` 报 `DOUBLE value is out of range`（搜索 500）；已执行 `OPTIMIZE TABLE posts` 重建并复测 search 200（0.06s）。后续容量测试清理后需补这一步。
