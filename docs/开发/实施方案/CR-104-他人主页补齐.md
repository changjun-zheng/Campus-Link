## 1. 目标

把 PRD [F-ACC-002](../../需求/产品需求文档.md) 的验收句补到能逐字签：「可见上述公开信息及其**发帖回帖时间线**」——当前 `/u/:id` 主页（`ProfileView.vue`，332 行实页，随 [CR-077](../../变更日志/变更台账.md) / [CR-078](../../变更日志/变更台账.md) 交付）只有**资料卡 + 帖子时间线**，缺**获赞数、被采纳数、他人视角回帖时间线**三项。量化口径：`UserProfileVo` 多出 2 个计数、新增 1 个公开端点 `GET /api/v1/users/{id}/replies`、主页可切「帖子 / 楼层」两条时间线；`mvn verify` 全绿且**反证两支各自变红**、`npm run lint` exit 0、契约再生成 v1.19、**零迁移 / 零新依赖 / 零新错误码**。

**立论前的一次纠偏**：本轮开工取证发现[问题清单](../../项目现有问题清单.md) F-003 行仍是 2026-09-19 的文本（"`/u/:id` 仍指向 `Placeholder.vue`、无 `/u/{id}/posts`"），而代码里这两条早已交付 ⇒ **本方案按实测而非按清单旧文本立论**，并同批把该行回写、登记一条漂移（见 §2 ④）。

## 2. 范围

- **做**：
  1. **forum 侧三个聚合**：`PostRepository.sumVisibleLikeCountByAuthor`（`SUM(like_count)` WHERE 父帖可见）、`ReplyRepository.sumPublishedLikeCountByAuthor`、`ReplyRepository.countAcceptedByAuthor`（`is_accepted=1`），经 `ForumQueryApplicationService.authorStats(long)` **一次**返回 `AuthorStats(postCount, likeCount, acceptedCount)` 载体（不让 web/application 为一位数来回跨上下文三次）；
  2. **profile 出参加两字段**：`UserProfileApplicationService.PublicProfile` 与 `UserProfileVo` 各 +`likeCount` / `acceptedCount`，沿用现有 `int` 饱和收窄；`postCount` 改从 `authorStats` 一处取，**消除两处 WHERE 不同源的风险**；
  3. **他人视角回帖时间线**：新增 `GET /api/v1/users/{id}/replies`（公开，`@PublicEndpoint` + `@ErrorCodes(USER_NOT_FOUND)`，落在既有 `UserPostController`）→ `ForumQueryApplicationService.listPublicRepliesByAuthor` + `ReplyRepository` 分页方法 + `PublicReplyItem` / `PublicReplyVo`（`id/postId/postTitle/summary/floorNo/createdAt`，**不下发 `contentMd`、不下发 `status`**——他人视角只给可见楼层，`status` 恒 PUBLISHED 属噪声）；可见性口径 = 楼层 `status='PUBLISHED' AND is_deleted=0` **且父帖同口径**，与 `listVisiblePostsByAuthor` 同源（与本人 `/replies/mine` 的"被下架要出现并带 `status`"**刻意相反**）；
  4. **前端**：`api/user.ts` 加 `getUserReplies` 与两字段类型；`ProfileView.vue` 资料卡计数 3 → 5（发帖 / 获赞 / 被采纳 / 粉丝 / 关注），下方加「帖子 / 楼层」自有文字型 Tab（沿用 CR-091 首页 Tab 样式，不复用 EP 组件），楼层条目点标题跳 `/posts/{postId}`；路由参数切换**复用现有 `reqSeq` 序号守卫**，新增一条时间线不得绕过它；
  5. **同批文档**：契约再生成 v1.19 + 技术方案 §5 补一行与两个计数字段口径；问题清单 F-003 行按实测回写（原句保留为时点快照 + 加实测注），**新登记 E-016**（清单行落后代码两轮，属 E-007 / E-009 同类漂移）；界面规范 §5.1 补"主页计数行现行顺序"。
- **不做（逐条给理由）**：
  - **头像上传与 `avatarUrl` 下发**——需对象存储与文件面依赖，属新基础设施，另开 CR；
  - **`school` / `grade` 下发**——注册链路零写入（[E-012](../../项目现有问题清单.md)），且「级」已被发起人 09-19 定调不展示；
  - **「届」徽章**——CR-036 草案已判「循环取证、不排期」，本 CR 不使其复活；
  - **提问侧「已解决帖数」**——只做回答侧被采纳数（见 D-2），两个数并排会在一张卡上互相抢焦点；
  - **访客计数 / 主页浏览记录**——PRD 无此项，且需要新写路径与审计；
  - **回帖时间线的 IP 限流**——与既有 `/{id}/posts` 同姿态（只有资料端点因 09-19 那次决策带 30/min 限流），不给同一条链路装两套门。

## 8. 实施结果（实施后追加，不回改上文）

**实施完成（2026-10-15）。发起人当轮批复：确认方案开工 + D-1 取「帖子 + 楼层获赞之和」+ D-2 取「回答被采纳次数」+ D-3 加「我的收藏」入口。**

- **改动**：后端 forum 侧新增端口三条（`PostRepository.sumVisibleLikeCountByAuthor`、`ReplyRepository.sumVisibleLikeCountByAuthor` / `countAcceptedVisibleByAuthor`）+ 分页一条（`findPublicPageByAuthor`），SQL 全部落 `@Select` 字面量；新增领域载体 `PublicReplyRow` 与查询行 `PublicReplyDO`；`ForumQueryApplicationService` 加 `authorStats(long)` → `AuthorStats(postCount, likeCount, acceptedCount)` 与 `listPublicRepliesByAuthor`；account 侧 `UserProfileApplicationService.PublicProfile` 与 `UserProfileVo` 各 +2 字段（`postCount` 改由 `authorStats` 单点取，消除两处 WHERE 分写）；web 新增 `GET /api/v1/users/{id}/replies`（`UserPostController` 第二个映射方法）+ `PublicReplyVo`。前端 `api/user.ts` 加 `getUserReplies` 与两字段，`ProfileView.vue` 计数 3 → 5、「帖子 / 回帖」双 Tab、本人态「我的收藏」入口。**零迁移 / 零新依赖 / 零新错误码**（`like_count`、`is_accepted` 均 V1 就位，`author_id` 有 FK 索引）。
- **验证（实测）**：`mvn -B -o verify` → **Tests run: 381, Failures: 0, Errors: 0, Skipped: 4** + `BugInstance size is 0`（SpotBugs 与 jacoco 60% check 同批通过，`ArchitectureGuardTest` 12 例不破）；新增 **15** 例（`ForumQueryApplicationServicePublicTimelineTest` 9 例 + `ReplyMapperPublicTimelineSqlTest` 6 例）；`npm run lint` exit 0、`npm run build` 通过；契约再生成 **v1.19**（**+158 / −0**，结构化比对判**纯新增**：既有 41 operation 与既有 schema 逐项 byte-identical、`UserProfileVo` 由 8 位增至 10 位）。
- **两支反证各自变红后复原**：① 摘掉公开楼层 SQL 的父帖可见性两个条件 → `publicTimelineFiltersBothReplyAndParent` 红；② 摘掉 `is_accepted = 1` → `acceptedCountRequiresVisibleContent` 红（`Tests run: 6, Failures: 2`）。`ReplyMapper.java` 复原后 sha256 `b31d9ced…` 与实验前逐字节相等。
- **真机（起 MySQL / Redis / 8088 / 5173 全栈）**：以开发库为样本逐位核对——**5 个用户（1 / 25 / 31 / 32 / 33）的 `postCount` / `likeCount` / `acceptedCount` 与楼层 `total` 全部等于独立 SQL 计算值（5/5 PASS）**；其中 **user 32 是一条天然对照样本**（26 帖仅 6 可见、隐藏帖带 3 个赞 → 接口获赞回 0，证明可见性过滤在真链路上真的生效）；楼层条目出参字段实测为 `id/postId/postTitle/floorNo/summary/createdAt`，**无 `status`、无原文**；不存在用户 → `404 / 2007` 与资料端点同码；匿名 `POST /api/v1/posts` 仍 `401`（主链路回归不破）。浏览器实测（chrome-devtools 起可见页面）：`/u/25` 显示 `0 帖子 / 1 获赞 / 1 被采纳 / 0 粉丝 / 0 关注` 与库中一致，点「回帖」Tab → `aria-pressed=true`、共 4 条、楼层四件套齐、无「已下架」标签；`/u/25 → /u/32` 切用户后 `activeTab` 复位到「帖子」且数据无残留（`reqSeq` 守卫有效）；本人态 `/u/32`（以 dev-stu-01 登录）出现「编辑资料 + 我的收藏」两个入口、无关注按钮。
- **偏差与遗留（如实登记）**：① **「被采纳数在父帖下架时应排除」这一分支没有真机样本**——开发库 4 条 `is_accepted=1` 的楼层父帖全是 `PUBLISHED`，验不到该分支；本轮**未做写入型实验**（要下架一条带被采纳答案的帖会在 dev 库留处置审计行并触发热榜置 0），该分支只由 `ReplyMapperPublicTimelineSqlTest` 的注解字面量断言守；② `PostMapper` 的 SUM 条件与 `visibleQuery()` 是**两处各写一遍**（SQL 字面量 vs Lambda 构造器），已由该测试断言三个条件都在，但**新增可见性条件时两处都要改**，这是本 CR 留下的维护面；③ **契约 v1.19 来源＝未提交工作区 ⇒「提交后核对」挂账**——**〔2026-10-15 后续：该挂账已闭环〕** CR-104 随 `849dd8e` 提交推送后自提交树重抓，与归档快照 `cmp` 逐字节相等（sha256 `81da872016c24475…`），依据写在[契约 README](../../设计/接口契约/README.md) §2 的「v1.19 提交后核对」行；快照文件零改动；**④ 头像与 `school` 下发按不做清单未动；⑤ 内置浏览器（Qoder in-app）在 `visibilityState=hidden` 下卡在 `route-fade-leave-active`、`router-view` 不挂载（CR-091 记过的同类现象），故浏览器实测改用可见 Chrome——**这是工具面现象，非本 CR 缺陷**。
