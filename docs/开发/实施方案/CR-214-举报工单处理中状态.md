## 1. 目标

PRD F-ADMIN-003 要求工单状态闭环为「待处理 → 处理中 → 已闭环」，当前实现只有 `PENDING → CLOSED`，两名运营同时处理时无法表达「已被认领」。V1 的 `reports.status` 注释已预留 `PROCESSING`、`handler_id` 列也已存在，本 CR 补上认领动作与状态流转，零迁移。

## 2. 范围

- **做**：
  - 新增 `POST /api/v1/admin/reports/{id}/claim`（OPS / SUPERADMIN）：`PENDING → PROCESSING`，写 `handler_id`，记 `REPORT_CLAIM` 审计。
  - 闭环允许从 `PENDING` 或 `PROCESSING` 完成（`close` 的条件更新改为两态）；重复处理仍幂等 200。
  - 举报人对被举报内容的隐藏持续到**闭环**：`findPendingTargetsByReporter` 改为包含 `PENDING + PROCESSING`，重命名为 `findUnclosedTargetsByReporter`。
  - 工单列表 status 过滤支持 `PROCESSING`；管理后台工单区增加「处理中」筛选、状态标签与「认领」按钮，处理中也可直接处置 / 驳回。
  - 看板举报组增加 `reportProcessing` 计数（total = pending + processing + closed），前端看板同步。
  - 单测、契约快照、技术方案 §5、台账 / 驾驶舱 / 文档索引同步。
- **不做**：
  - 不改表结构（零迁移）、不新增错误码；不存在 → `404 / 3001`，已认领 / 已闭环重复认领 → 幂等 200（不重复审计）。
  - 不强制「必须先认领才能闭环」——保留快速驳回路径。
  - 不做工单转派 / 取消认领 / 处理时限；不改举报提交与 24h 去重。

## 5. 验证

- **单测**：认领 PENDING 写 PROCESSING + handler + 审计；认领 PROCESSING / CLOSED 幂等零审计；并发认领失败不审计；闭环从 PROCESSING 成功；隐藏目标查询包含两态。
- **真机**：举报后举报人列表不可见；认领后仍不可见；驳回后恢复可见；处置后保持下架。看板 reportProcessing 与实际行数一致。
- **前端**：管理后台「待处理 / 处理中 / 已闭环」筛选可用，认领后行内状态即时更新；浏览器无控制台异常。
- **契约**：新增 1 个 POST 操作与 `reportProcessing` 属性，其余结构化零变化。
- **回归**：匿名 / 普通用户 401 / 403；重复闭环幂等；举报提交与去重不变。

revert 本 CR 提交即可；零迁移、零数据回补。已进入 PROCESSING 的工单会被旧代码视为「非 PENDING」，旧版闭环会拒绝——回滚前须把 PROCESSING 工单批量置回 PENDING（单条 SQL，按需执行）。
