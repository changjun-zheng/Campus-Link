验收修复：异步通知到达时，通知页首屏列表可能已加载，造成角标变化但列表不变。通知页现在观察现有共享未读状态刷新，并用请求序号阻止迟到结果覆盖；继续复用一条 SSE，不新增接口、依赖或样式。

故障注入边界：确认超时、nack、returned 由受控单测验证；发布进程崩溃／提交后确认前崩溃通过租约状态及提交后同 ID 重投复现其恢复状态，未在准确指令窗口强杀进程。未进行集群切换、磁盘损坏、长期压力或生产环境验收。

## 2. 本机环境与保留数据

复用本机 RabbitMQ 4.2.5／Erlang 与 MySQL 8 已安装二进制，没有安装升级服务、改动 .env／凭据文件／CI 或修改服务权限。Windows 原生服务启动权限不足，使用用户态独立实例：MySQL `127.0.0.1:3307`，RabbitMQ `127.0.0.1:5673`、节点 `campuslink_cr193@localhost`，异步后端 8089，同步对照 8090，前端 5183／5184；Redis 使用既有本机 6379。所有 CLI 数据核对先设 UTC 会话。

MySQL 验收目录为 `D:/Workspace/cr193-runtime/mysql`，运行日志同目录；RabbitMQ 验收数据位于本机临时目录 `campuslink-cr193-rabbit`。临时目录在续接时曾留下空数据库目录，因此本轮改用独立工作目录重建数据库并重新浏览器验证。原开发数据库未连接、未改动；合成账号、帖子及故障证据保留，未清理消息或表。

隔离 RabbitMQ 死信中保留两条无效探针：首次手工构造重复消息时误用数据库小写 type，而消息协议要求大写枚举。该探针没有生成额外通知，随后改用合法事件重新验证重复消费。重放命令成功跳过并保留这两条无关消息，只转移指定的合法 eventId；详情在故障记录中。它们会触发预期死信告警，不属于线上积压；不得直接对原消息原样重放并期待类型错误自行修复。

## 3. 启用与监控

同步模式无需 RabbitMQ。异步模式在进程环境设置以下变量，再按项目常用命令启动后端（本机开发不使用 Docker）：

| 变量 | 用途 |
|---|---|
| `NOTIFICATION_RABBITMQ_ENABLED=true` | 创建发布器、监控器、监听器与拓扑 |
| `NOTIFICATION_DELIVERY=rabbitmq` | 将六类互动通知写 Outbox；缺省 sync |
| `RABBITMQ_HOST`／`RABBITMQ_PORT`／`RABBITMQ_VHOST` | 缺省 127.0.0.1／5672／`/`，按环境指定 |
| `RABBITMQ_USER`／`RABBITMQ_PASSWORD` | 必须外部注入；开启集成时缺少任一启动失败，不在文件中填写可用凭据 |

拓扑：direct exchange `campuslink.notifications` → `campuslink.notifications.v1`；死信 exchange `campuslink.notifications.errors` → `campuslink.notifications.dead.v1`；两条绑定均用 `notification.requested.v1`。交换机、队列、消息持久化；单消费者、prefetch 20。

Micrometer 指标：`campuslink.notification.outbox.pending`、`campuslink.notification.outbox.oldest.seconds`、`campuslink.notification.publish.failures`、`campuslink.notification.consume.failures`、`campuslink.notification.dead.pending`、`campuslink.notification.dead.letters`。每 10 秒采样积压；最老等待超过 60 秒、死信大于零或死信探测不可用时，最多每 60 秒输出一条 `Notification backlog` 告警。指标注册于现有 MeterRegistry；本轮没有开放公网 metrics 或消息维护端点。阈值告警不替代外部值守和单节点磁盘监控。

本机查积压（先使用现有授权账号连接数据库，不在命令中填写口令）：

```sql
SET SESSION time_zone='+00:00';
SELECT status, COUNT(*) FROM notification_outbox GROUP BY status;
SELECT event_id, attempts, next_attempt_at, locked_until, last_error
FROM notification_outbox WHERE status <> 'SENT' ORDER BY occurred_at LIMIT 20;
SELECT event_id, consumed_at FROM notification_receipts WHERE event_id = '<eventId>';
```

不要把 SENT 当成已消费：发布确认转移的是消息持有责任，消费凭证才证明已处理（含拉黑／自触发抑制）。不允许为了解除告警而删凭证；这会破坏历史重放的幂等性。

## 4. 死信检查与重放

先检查原因、修复依赖或业务失败，再在仓库根目录执行。要求 Java 21、Maven、Python；`JAVA_HOME` 与上表连接变量由当前进程环境提供。脚本只在 backend/target 生成编译与依赖缓存，不修改凭据文件。

```powershell
python backend/scripts/notification_replay.py <eventId>
```

命令按消息属性 messageId 匹配，只扫描当前队列快照（最多 10000 条）；未命中消息保持未确认，结束时重新入队。指定消息原 body、原 eventId、持久化、mandatory + confirm 发送到主交换机，确认且未被退回才确认死信原消息。失败保留原消息；找不到 ID 非零退出。保持通知监听器运行；命令完成后核对消费凭证、通知与剩余死信，不以“重放已发送”代替消费成功。

无效 JSON／不支持的 schemaVersion／错误类型需要先查事件来源和代码兼容性；本命令不修改载荷、不伪造新 ID，也不自动清理死信。多条相同 ID 的死信逐条重放时，消费端仍只允许一条通知。

## 5. 回滚

将 `NOTIFICATION_DELIVERY=sync`，保持 `NOTIFICATION_RABBITMQ_ENABLED=true`，重启后新业务同步通知、既有积压继续投递。核对 Outbox 待发／处理中、主队列含未确认消息以及全部死信均已处置，再关闭集成。Broker 不可用时先恢复同步业务，保留待发记录等待恢复补发；不要删表、凭证、队列或消息，也不要改已执行迁移。旧版本部署前必须确认能否继续处理残留事件。

## 6. 可靠性依据

至少一次投递与消费去重参考 [RabbitMQ Reliability Guide](https://www.rabbitmq.com/docs/reliability)；监听恢复与确认转存参考 [Spring AMQP 恢复说明](https://docs.spring.io/spring-amqp/reference/amqp/resilience-recovering-from-errors-and-broker-failures.html)；correlated confirm 与 returned 的先后保证参考 [Spring AMQP RabbitTemplate](https://docs.spring.io/spring-amqp/reference/amqp/template.html)。外部资料用于设计核对，本项目具体行为以源码、测试和上述真实证据为准。
